## Earlier this session (2026-10-22): AI-driven review replaces manual admin approval for scanned foods/supplements (built, locally verified, not yet deployed)

Aravinth: *"instead of admin approving, can we use Ai with label knowledge to review and approve based on guidelines"* — asking to automate the "promote a pending scan to the shared catalog" step that both scan features below originally shipped with (Aravinth running a SQL `UPDATE` by hand). Scoped via one explicit choice, in his own words, when offered a hybrid (AI auto-approves clean cases, holds doubtful ones in a human-review queue) vs. full AI autonomy: *"Auto Approve clean cases, doubtful cases immediately reject with reason so the user can redo the same with the inputs."* **This is a strictly binary outcome — there is no queue, no "awaiting human review" state in normal operation.** A submission is checked once, immediately, and either joins the shared catalog or is kept private with a specific, actionable reason so the person can fix their input and rescan right away.

**`api/ai-helpers.js` gets a new `review-submission` kind** — the first kind in this file that also needs direct database access (via `lib/supabase-rest.js`'s service-role client, same pattern `api/telegram-webhook.js` already uses). It re-shows Claude the SAME photo the person originally scanned, alongside exactly what they saved (after their own review/edits), and asks for one of exactly two verdicts — "approved" or "rejected" — with instructions to reject rather than guess whenever genuinely unsure, since rejecting is cheap (the person just rescans) and a doubtful row silently joining the shared catalog is not. Reject triggers: a saved number that clearly disagrees with what's printed (not ordinary rounding), a mismatched serving size, a spam/gibberish/placeholder product name or brand, a saved value that looks like a %RDA percentage rather than an absolute amount (supplements only — this app never stores that), calories wildly inconsistent with saved protein/carb/fat (packaged foods only, with slack for fiber/rounding and skipped whenever any of the three is null), or a photo that doesn't actually show a legible label. An honest null/missing field is explicitly never a rejection reason. A rejection must carry one short, specific, actionable sentence (e.g. "The label shows Vitamin C as 40 mg but 400 mg was saved.").

**The architectural reason this is safe:** `foods`' RLS policies have deliberately never given the browser (`authenticated` role) an UPDATE policy at all — only an INSERT policy for its own `pending` row (see both scan features below). So the browser cannot self-approve under any circumstance; only this new server-side endpoint, authenticated with `SUPABASE_SERVICE_ROLE_KEY`, can transition a row to `approved` (clearing `owner_user_id`, which is what actually promotes it into the shared catalog) or `rejected`. A row only ever changes state after an actual Claude verdict against the actual stored photo — never a client-asserted "trust me." The UPDATE itself is guarded by `review_status=eq.pending` (an idempotency check: a retried/duplicate review call can't re-process, and can't flip, an already-decided row) and, separately, by its own try/catch: if the Claude call fails outright, or its response can't be parsed as the expected JSON shape, the row is left exactly as it was (`pending`) rather than guessing either way — and if a verdict IS reached but the database write itself then fails, that's reported as its own distinct error (naming the verdict that was reached) rather than silently claiming success.

**New `add_ai_review.sql`** — one new column, `foods.review_notes` (text; the rejection reason, or null on a clean approval). No RLS policy changes at all, and that's the point being verified: the browser still has no UPDATE policy on `foods`, so it still can't write `review_notes` (or anything else) on its own row, no matter what. **Verified against a real local Postgres 16 instance**, extending the project's established two-user RLS test pattern with a new user pair (Carol/Dave): confirmed the browser role cannot self-approve its own pending row (the UPDATE is rejected, and the row is independently confirmed unchanged — still `pending`, still owned); confirmed the browser role cannot write `review_notes` either, by itself, on the same row; confirmed a service-role-style connection (bypassing RLS, same privilege as `SUPABASE_SERVICE_ROLE_KEY`) CAN approve with a `review_notes` reason; confirmed the `review_status=eq.pending` guard is meaningful — a first service-role UPDATE on a pending row succeeds (rejects it with a reason), and a second, differently-shaped UPDATE attempting to then approve that SAME row is correctly a no-op (0 rows affected) because it's no longer `pending`; and confirmed the shared-catalog/private-row visibility split still holds end-to-end afterward (an approved row is visible to another user, a rejected row stays visible only to its own submitter).

**`index.html`:** both `pkSaveBtn.onclick` (packaged food) and `supSaveBtn.onclick` (supplement) now call a new shared helper, `submitForAiReview()`, immediately after their `foods` insert succeeds — passing the food's id, product type, the same photo already held in memory for that scan, and the exact values the person saved (after their own edits). This helper is a genuinely shared *mechanism* (one POST call, no business rules of its own), unlike the rest of each scan flow's code, which stays deliberately duplicated between the two per this project's established convention. The old generic "Aravinth's team reviews new scans before they join the shared catalog" status message is gone; the person now sees one of three honest outcomes within a couple of seconds of saving: **approved** ("checked against the label and added to the shared catalog for everyone"), **rejected** (the specific reason, plus a note that today's log entry is untouched and they can rescan with corrected values), or, only if the review call itself couldn't be completed, an honest **"couldn't automatically verify it against the label just now"** message distinct from a real rejection — the item stays in their personal list either way, nothing is lost.

**Verified with a mocked-fetch Node test harness, 32/32 checks**, covering: the approve path's exact UPDATE shape (clears `owner_user_id`, sets `review_status='approved'`, `review_notes=null`); the reject path (reason captured verbatim into `review_notes`, `owner_user_id` left untouched); a Claude-call failure leaving the row untouched (`pending`) with no DB write even attempted; an unparseable Claude response handled the same way, distinctly from an actual rejection; a verdict that WAS reached but whose database write then fails, reported as its own distinct error naming the verdict; missing-field validation rejecting the request before any network call at all; and that all of the file's pre-existing kinds (including the unknown-kind error message, now listing `review-submission`) are unaffected by this addition. ### Decision: no race/ethnicity input in the energy-needs model

Aravinth asked how the model should vary energy/nutrient needs by race and by age group. Researched this (see chat for sources) before answering: NutriGap's `computeTargets()` already varies energy needs by age (direct term in the Mifflin-St Jeor BMR formula) and sex, and varies micronutrient DRI targets by a 6-bracket age table — all pre-existing, no gap there. Race/ethnicity deliberately stays **out** of the energy formula: real but small measured RMR differences between some racial groups persist even after adjusting for body composition (~5% in one well-cited study), but the effect is too weak and inconsistent for mainstream dietetics to have adopted a race-specific version of Mifflin-St Jeor (the equation's own original validation didn't even report its sample's racial makeup) — so NutriGap's current race-agnostic approach matches standard practice, not a shortfall. Where ethnicity genuinely matters more is a separate question: WHO recommends lower BMI cutoffs for Asian populations for overweight/obesity risk classification (≥23/≥27.5 vs. the standard ≥25/≥30), since Asians carry more visceral fat and face elevated diabetes risk at a lower BMI — relevant to BFB's mostly-Indian customer base if a "healthy weight band" feature is ever added, but NutriGap doesn't compute or display BMI at all today, so this isn't fixing an existing gap. No code changed from this — it's a recorded decision so a future session doesn't redo the research or assume race belongs in the kcal formula.
